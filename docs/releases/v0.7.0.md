# v0.7.0

Covering v0.5.0 to v0.7.0: everything merged into `main` up to and including commit `abb18900902af385a01f73afe90a1c96917c591a`, of November 19, 2026, 23:01 PST. The v0.7.0 tag names that commit, not `main`'s tip, so work that landed after it belongs to the next release however long these notes take to land. This file landed on `main` after that commit, so the tag does not contain it. A release workflow that reads notes from `main`, as the one on `main` now does, publishes this file as the release page when the tagged commit is one that has that workflow. A tag at the commit named above has an older workflow that cannot, so its page carries the install instructions alone; whoever cuts such a tag puts these notes on the page afterwards, from a checkout of `main` that carries this file: `bash scripts/release-body.sh v0.7.0 body.md`, then `gh release edit v0.7.0 --notes-file body.md`. The release date is the tag's.

v0.6.0 was never tagged. Its notes landed on `main` as [`v0.6.0.md`](v0.6.0.md), but no tag followed them, so everything they describe ships here, in v0.7.0, together with what has merged since. That file is kept as the record of what was prepared then.

This release is about the factory keeping itself moving. The stall fixes come first: moving onto a new build no longer cancels working runs or holds the merge queue up, a free developer slot is filled or the reason it is not is recorded, and an approved change stopped by the tracker, GitHub or the network resumes by itself once they answer. Beside them come checks on CI, where a run waits for GitHub's required checks on the exact commit instead of running the whole suite locally; a merge queue that picks by priority, checks one candidate ahead and recovers from GitHub's refusals on its own; a tracker store held within its size limit; MCP tools that roles and developer runs reach only through the harness, with a setup guide; and working beside a team's own branch and a companion intent repository. Everything v0.6.0's notes describe is carried into the entries below.

804 work items closed with a change on `main` between v0.5.0 and that commit: the 632 v0.6.0's notes named, and 172 since. They are grouped here by what they changed rather than listed one by one, so these notes stay readable and within what a release page can carry; every one of them is named by its identifier under the entry it belongs to, and the tracker holds each item's full description.

Each entry below names the goals its work served, by the identifier the goals documents give them:

- `[nearly-autonomous]` Run development nearly autonomously.
- `[traceable-chain]` Maintain a traceable chain from the product brief through goals, designs, work, code changes, and verification.
- `[plain-language]` The harness's surfaces read clearly: boundaries between topics and speakers are visible, important findings stand out, every distinction survives a terminal that cannot render emphasis, and user-facing language chooses the ordinary, literal word over metaphor, coinage, or term of art.
- `[configurable-safely]` Keep roles, policies, and provider selection configurable without making safety invariants optional, and support multiple providers behind one adapter contract.
- `[isolated-worktrees]` Isolate implementation tasks in harness-managed Git worktrees and integrate successful work automatically.
- `[independent-review]` Every change is reviewed against the intent it claims to serve, by a role that did not write it, before it is integrated.
- `[no-silent-redefinition]` Let configurable agent roles collaborate without allowing downstream agents to silently redefine upstream intent.
- `[spend-follows-the-work]` Spend follows the work: the model, the context, and the number of provider calls a task costs are chosen for that task rather than for the role that does it, and running cost is visible and classified so the operator can see what each kind of work costs and decide what it should.
- `[readme-first-run]` A newcomer can go from the documented install to a working first run on their own repository using the readme alone.
- `[visible-spend]` The operator can see what the harness spends on their behalf: provider-reported cost, per work item, per run, and in total.
- `[internal-week-bar]` Before any outside trial, Yoyodyne runs one week on its own repository in which no hour passes with ready work waiting and a developer slot idle, nothing is asked of the owner that the harness or a role could have done, and the management roles' spend is at most 40% of all known spend for the week.
- `[harness-publishes]` Publish that work as pull requests the harness opens, and has the forge merge, on the roles' behalf, for projects that enable it, without letting any agent push or merge.
- `[shared-repository]` A team can run Yoyodyne against one shared repository: collaborators each run their own harness without losing work, splitting the tracker, or weakening any safety invariant.
- `[any-language]` Support development in any language.
- `[owner-attention-measure]` Yoyodyne is measured by useful software delivered per hour of the owner's attention.

## Key functionality

- **Moving onto a new build no longer stops working runs or holds the factory up**
  Serves: `[nearly-autonomous]`, `[internal-week-bar]`, `[isolated-worktrees]`

  Every change that lands is a new build, and moving onto it used to cancel developer runs mid-work, cut off the merge queue's check in progress, and hold back new work for up to fifteen minutes each time, eleven times on one day. A move now keeps a working run so it carries on, leaves the queue's check running, pauses new work and management passes as briefly as it can, and fills a free developer slot while it waits. Moves happen at most once every three hours, onto the newest installed build, with the interval a project setting between one and twenty-four hours. A run in flight at a move is carried on or stopped with its reason at once, a setting added by a landed change never stops parts still on an older build from loading the configuration, and status shows what a move is waiting for and since when. A scheduler whose wind-down for a move outlasts its limit restarts onto the new build, and is restarted for it if it has not within five minutes.
